# 插件机制迁移评估

## 目标

本文只回答一个问题：在当前已经完成“接口语义明确、场景调用明确、数据来源明确”的前提下，MusicPilot 的“插件后端 -> 宿主能力”这一层，哪些能力值得从宿主 HTTP API 迁到 MoviePilot 插件机制，哪些不值得。

本文不包含：

- 立即迁移实现
- 新增功能
- 新的策略系统
- 对 `./MoviePilotPkg` 或 `./MoviePilot-Plugins` 的任何修改

本文保留一个前提：

- `插件前端 -> MusicPilot 插件后端 API` 这一层仍然保留
- 本文评估的是 `MusicPilot 插件后端 -> MoviePilot 宿主能力` 这一层

## 当前接入全景

| 能力 | 当前接入方式 | 当前主接口/主语义 | 当时采用原因 |
| --- | --- | --- | --- |
| 搜索 | 宿主 HTTP API | `/api/v1/search/title`、`/api/v1/search/media/{mediaid}` | 语义已验证，最容易从插件外部后端发起请求 |
| 下载 | 宿主 HTTP API | `/api/v1/download/`、`/api/v1/download/add` | 已有真实成功样例，且 payload/response 已在 MusicPilot 中收敛 |
| 整理预览 | 宿主 HTTP API | `/api/v1/transfer/name` | 当前 preview/apply 模型已用此接口映射成功 |
| 整理执行 | 宿主 HTTP API | `/api/v1/transfer/manual` | 已有真实成功样例，先保证链路可跑 |
| 历史查询 | 宿主 HTTP API | `/api/v1/history/download`、`/api/v1/history/transfer` | 读取型接口，便于 path handoff 与历史回看 |
| 存储 | 当前未直接接入 | 无 | 现阶段未扩到存储能力，只通过 organize 侧间接依赖宿主 |
| 工作流 | 当前未直接接入 | 无 | 当前未展开工作流域 |

## 插件机制能力说明

### `get_api()`

- 作用：插件对外暴露自己的 API
- 适合承接：
  - MusicPilot 自己的插件后端接口
  - 插件前端调用插件后端
- 不适合承接：
  - 深度替代宿主内部链路
- 原因：
  - `get_api()` 解决的是“插件向外暴露什么”，不是“插件如何更深地参与宿主业务编排”

### `get_module()`

- 作用：插件重载/胁持宿主模块方法
- 适合承接：
  - 下载器、媒体服务器、存储等模块能力扩展
  - 整理链路里明确属于宿主模块职责的部分
- 不适合承接：
  - 简单的只读查询
- 原因：
  - `MoviePilot-Plugins/README.md` 明确把它定义为“重载系统模块功能”
  - 宿主 `chain` 会优先运行插件声明的方法，再落回系统模块

### 链式事件

- 作用：在宿主处理链中同步插入、拦截或补充处理
- 适合承接：
  - `TransferRename`
  - `TransferIntercept`
  - `ResourceDownload`
  - `StorageOperSelection`
  - `WorkflowExecution`
  - `MediaRecognizeConvert`
- 不适合承接：
  - 纯只读历史查询
  - 仅仅为了复用现有 HTTP 响应结构
- 原因：
  - 这是宿主内部编排的第一优先级扩展位，最适合“业务过程中的能力插入”

### 工作流动作 `get_actions()`

- 作用：把插件动作接入宿主工作流编排
- 适合承接：
  - 面向工作流用户可编排的插件动作
  - 将插件功能串到宿主工作流中
- 不适合承接：
  - 替代基础搜索、下载或历史查询 API
- 原因：
  - `get_actions()` 更像“把插件能力挂到宿主工作流 UI/引擎”，而不是底层能力接入

### 宿主模块直调

- 作用：直接使用宿主 `chain` / `modules` / `StorageChain` / `TransferChain` / `DownloadChain`
- 适合承接：
  - 存储
  - 整理
  - 工作流协同
- 不适合承接：
  - 需要保持低耦合、独立部署或独立调试的简单 HTTP 语义
- 原因：
  - 能减少 HTTP 映射层，但会显著提升版本耦合

## 宿主接口与插件机制对应关系

### 搜索

- 当前 HTTP 语义：
  - `/api/v1/search/title` 是标题搜索
  - `/api/v1/search/media/{mediaid}` 是媒体 ID 精确搜索
- 宿主内部实际依赖：
  - `SearchChain`
  - `MediaChain`
  - `ChainEventType.MediaRecognizeConvert`
- 结论：
  - 搜索本身已经是宿主内部成熟链路，HTTP 层只是薄包装
  - 迁到插件机制不会显著简化 MusicPilot，反而会让 MusicPilot 直接依赖 `SearchChain`/`MediaChain` 细节

### 下载

- 当前 HTTP 语义：
  - `/api/v1/download/`：含 `media_in` 的下载
  - `/api/v1/download/add`：只给 `torrent_in`，由宿主识别媒体
- 宿主内部实际依赖：
  - `DownloadChain`
  - `MediaChain`
  - `Context` / `MediaInfo` / `TorrentInfo`
- 结论：
  - 两个 HTTP 接口已经准确映射两类下载语义
  - 若迁到宿主内直调，MusicPilot 会直接耦合宿主内部数据结构，复杂度上升快于收益

### 整理

- 当前 HTTP 语义：
  - `/api/v1/transfer/name`：命名预览
  - `/api/v1/transfer/manual`：人工整理执行
- 宿主内部实际依赖：
  - `TransferChain`
  - `StorageChain`
  - `TransferHistory`
  - `FileItem`
  - `ChainEventType.TransferRename`
  - `ChainEventType.TransferIntercept`
- 结论：
  - organize 是当前最适合迁到插件机制的能力
  - 原因不是“HTTP 不能用”，而是 organize 本身就是宿主内部重链路，插件机制更贴近真实语义

### 历史

- 当前 HTTP 语义：
  - `/api/v1/history/download`：下载历史
  - `/api/v1/history/transfer`：整理历史
- 宿主内部实际依赖：
  - 历史表/模型查询
- 结论：
  - 历史更像只读查询接口
  - 继续保留 HTTP API 最简单，不值得为了“更内聚”去增加直调耦合

### 存储

- 当前状态：
  - MusicPilot 还没有单独扩展存储域
- 宿主机制线索：
  - `StorageChain`
  - `StorageOperSelection`
  - `get_module()`
- 结论：
  - 如果未来真的要扩展存储类型或文件操作，应优先走插件机制
  - 不建议先做一层新的 HTTP 包装

### 工作流

- 当前状态：
  - MusicPilot 还没有展开工作流域
- 宿主机制线索：
  - `get_actions()`
  - `ChainEventType.WorkflowExecution`
- 结论：
  - 如果未来要把 MusicPilot 集成到宿主工作流，优先用插件工作流动作/事件
  - 不建议绕回 HTTP API 再去调工作流

## 候选迁移项评估

| 能力 | 保留 HTTP API | 适合迁到 `get_module()` | 适合迁到链式事件 | 适合宿主模块直调 | 暂不建议迁移 | 判断 |
| --- | --- | --- | --- | --- | --- | --- |
| 搜索 | 是 | 否 | 部分相关，但不作为主迁移手段 | 否 | 是 | 继续保留 HTTP API 最合理 |
| 下载 | 是 | 部分可能，但收益不高 | `ResourceDownload` 有价值，但不适合作为第一轮迁移 | 部分可能 | 是 | 继续保留 HTTP API 最合理 |
| 整理 | 可暂保留 | 是 | 是 | 是 | 否 | 第一优先级迁移候选 |
| 历史 | 是 | 否 | 否 | 否 | 是 | 不值得迁移 |
| 存储 | 否 | 是 | 是 | 是 | 否 | 若未来进入该域，应优先插件机制 |
| 工作流 | 否 | 否 | 是 | 部分可能 | 否 | 若未来进入该域，应优先插件机制 |

## 迁移收益/代价表

| 候选项 | 语义更清晰 | 减少 HTTP 映射 | 更贴近宿主体系 | 版本耦合增加 | 测试复杂度变化 | 对现有前后端边界影响 |
| --- | --- | --- | --- | --- | --- | --- |
| 搜索迁移 | 一般 | 中 | 中 | 高 | 高 | 会穿透现有插件后端边界 |
| 下载迁移 | 一般 | 中 | 中 | 高 | 高 | 会让 MusicPilot 直接依赖宿主内部 `Context` |
| 整理迁移 | 高 | 高 | 高 | 中到高 | 中 | 影响较集中，最值得做 |
| 历史迁移 | 低 | 低 | 低 | 中 | 中 | 收益很低，不建议 |
| 存储迁移 | 高 | 高 | 高 | 中到高 | 高 | 若未来做存储域，值得直接按宿主方式接 |
| 工作流迁移 | 高 | 中 | 高 | 中 | 中 | 若未来做工作流域，插件机制天然更合适 |

## 推荐迁移顺序

### 第一优先级：整理能力

最推荐优先迁移 organize，不是搜索，也不是下载。

原因：

1. organize 当前最依赖宿主内部类型和处理链，HTTP 只是把 `transfer/name` 和 `transfer/manual` 映射出来。
2. 宿主已经为整理提供了非常明确的链式事件和模块扩展位：
   - `TransferRename`
   - `TransferIntercept`
   - `StorageOperSelection`
   - `TransferChain`
   - `StorageChain`
3. organize 是当前 HTTP 语义最“勉强可用但不够自然”的一块，迁入插件机制后更可能降低复杂度。

### 第二优先级：工作流/存储

前提是未来真的进入这两个业务域。

原因：

- 它们天然属于宿主内部编排和模块能力，不适合先扩成一层新的 HTTP 适配

### 低优先级或不建议：搜索、下载、历史

- 搜索：
  - 当前 HTTP API 已经是宿主 `SearchChain` 的薄包装
  - 迁入插件机制带来的收益不大
- 下载：
  - 当前 `/download/` 与 `/download/add` 已经准确反映两类不同语义
  - 迁入内部会放大 `Context` / `MediaInfo` / `TorrentInfo` 耦合
- 历史：
  - 只读查询最适合保留为 HTTP API
  - 迁移后只会增加复杂度

## 最小迁移方案

如果只做一轮最小迁移，最推荐迁的是：

- `organize apply / preview` 背后的宿主能力接入层

具体不是“改插件前端 API”，而是：

1. 保留 MusicPilot 自己的插件 API 入口不变
2. 只把 `MusicPilot 插件后端 -> 宿主 organize 能力` 这一层改成插件机制优先
3. 优先评估：
   - `TransferRename`
   - `TransferIntercept`
   - `StorageOperSelection`
   - 必要时的 `get_module()`

这条路径最可能带来：

- 更贴近宿主真实整理语义
- 更少的 HTTP 请求/响应映射
- 更少的“preview/apply 外部拼装”代码

同时它对现有边界的破坏也最小：

- 插件前端不用改
- MusicPilot 插件 API 不用改
- search / download / history 仍然保持当前已经验证过的 HTTP 语义

## 不建议迁移项

当前明确不建议优先迁移的能力：

### 搜索

不建议迁移的原因：

- 已有 HTTP 语义清晰
- 宿主链路内部复杂，但 HTTP 包装已经足够薄
- 迁移后会把 MusicPilot 绑死到宿主识别与搜索链内部细节

### 下载

不建议迁移的原因：

- `/download/` 与 `/download/add` 语义已经很稳定
- 迁入宿主内部后，MusicPilot 必须直接构造宿主 `Context`
- 会提高版本耦合和测试难度

### 历史

不建议迁移的原因：

- 读取型接口保留 HTTP 最直接
- 它不参与复杂业务编排，不值得为此引入宿主内直调

## 最终结论

### 继续保留 HTTP API 最合理的能力

- 搜索
- 下载
- 历史查询

### 第一优先级迁移能力

- 整理

### 如果未来进入新域，优先使用插件机制的能力

- 存储
- 工作流

### 如果只做一轮最小迁移，最推荐迁哪一块

- 最推荐迁 organize

原因：

- organize 最贴近宿主内部链路
- organize 迁移最可能真正减少当前 MusicPilot 的映射复杂度
- organize 迁移不要求同步重写 search / download / history

### 一句话判断

不要把所有宿主能力都迁到插件机制。  
真正值得优先迁的，是 organize；搜索、下载、历史继续保留 HTTP API 反而更简单。
