# 统一音乐媒体解析链设计基线

> 用途：记录 MusicPilot 在 metadata / discovery / search / subscription / acquisition / organize 上层统一采用的原始语义。本文描述的是长期设计基线；当前代码已经完成第一轮全局迁移，接管了 discovery/detail 主路径，并开始进入部分下游服务，但仍未完成全部场景收口。

## 1. 设计结论

MusicPilot 后续的上层统一语义确定为：

`MusicMediaInput -> MusicMetaBase -> MusicMediaInfo`

这条链参考 MoviePilot “统一媒体解析链”的设计方法，但不复用影视模型本身。

同时，后端组织方式也明确固定为 MoviePilot 风格的 `Chain` 模式：

- 主业务流程由 `*Chain` 统一编排
- `Chain` 负责阶段推进、状态管理与结果回写
- `Service` 只承担链的支撑职责，不再继续承担主流程编排
- 后端目录结构、文件命名与代码风格也应对齐 MoviePilot，而不是只对齐高层概念

也就是说，MusicPilot 将借鉴的是：

- 统一原始输入
- 统一中间元数据
- 统一正式媒体对象
- 各业务场景围绕同一条识别链复用结果

而不是继续让 discovery、detail、search、subscription、organize 各自维护一套零散解析逻辑。

## 1.1 后端目标结构

统一音乐媒体解析链与后端主流程的长期目标结构固定为：

- `backend/app/api/endpoints/`
- `backend/app/chain/`
- `backend/app/db/models/`
- `backend/app/db/*_oper.py`
- `backend/app/helper/`
- `backend/app/modules/`

说明：

- `api/routes`、`services`、`models`、`repositories`、`adapters` 不作为长期主结构保留
- 如重构过程中临时存在，只视为过渡层，最终必须退出活跃主路径
- API、scheduler、plugin service 入口应直接调用 `Music*Chain`

当前后端主链固定为：

- `MusicMediaChain`
- `MusicSearchChain`
- `MusicDownloadChain`
- `MusicTransferChain`
- `MusicSubscribeChain`
- `MusicChartChain`
- `MusicDashboardChain`

文件命名优先对齐 MoviePilot 的领域文件名，例如：

- `chain/media.py`
- `chain/search.py`
- `chain/download.py`
- `chain/transfer.py`
- `chain/subscribe.py`
- `chain/chart.py`
- `chain/dashboard.py`

类命名保留音乐领域语义，统一使用 `Music*Chain`。

## 2. 为什么要这样设计

当前项目虽然已经具备真实 metadata provider、真实 discovery provider、RSS lookup、metadata drawer 下钻等能力，但上层识别语义仍然存在以下问题：

- discovery 到 metadata 仍带有明显的过渡态 lookup/hints 痕迹
- 不同来源的解析逻辑分散在 parser、assembler、metadata lookup 等多处
- 同样的音乐线索还没有被抽成统一中间对象
- 后续 search、subscription、acquisition、organize 还不能稳定复用同一个正式音乐对象

因此，项目下一阶段不是继续局部补 case，而是建立统一音乐媒体解析链。

## 3. 三层核心模型

### 3.1 `MusicMediaInput`

原始输入层，表达“当前这个场景拿到了哪些音乐线索”。

它可来自：

- discovery 榜单条目
- metadata 搜索输入
- subscription 目标
- acquisition / dispatch 前上下文
- organize 上游线索
- 文件路径、文件名、标签等库内线索

它保留原始语义，但不承担最终识别结果。

### 3.2 `MusicMetaBase`

解析后的中间元数据层，对应 MusicPilot 的统一音乐识别输入。

这一层要完成：

- 标题、艺人、专辑、发行日期等字段的标准化
- aliases / candidate 归一化
- 外部引用的归一化
- 证据来源与强度的保留

它既不是前端展示对象，也不是 provider detail，而是后续统一识别链的中间基座。

### 3.3 `MusicMediaInfo`

识别后的正式媒体对象层，对应 MusicPilot 的统一音乐实体结果。

后续主链应尽量围绕它继续推进，包括：

- metadata detail
- search query builder
- subscription target
- acquisition / dispatch
- organize 上游输入

`MetadataDetail` 更适合作为 `MusicMediaInfo` 的富展示视图，而不是反过来主导整条链。

## 4. 统一识别原则

### 4.1 统一媒体解析链，而不是 detail 特判

“discovery -> detail” 只是统一音乐媒体解析链的一个消费场景，不是单独定义整个架构的入口。

同一条解析链后续还应服务：

- detail 下钻
- 搜索输入标准化
- subscription 目标确认
- 获取链路实体确认
- organize 上游元数据补全

### 4.2 强标识与弱线索统一收口

参考 MoviePilot 的设计方法，统一音乐媒体解析链内部应同时支持：

- 强标识直达
- 弱线索识别

但这两条路径都应收口到同一套 `MusicMediaInput -> MusicMetaBase -> MusicMediaInfo` 语义，而不是继续在外层暴露零散模式判断。

### 4.3 前端不理解来源差异

前端页面可以展示来源差异，但不应直接承担来源特判。

具体到 discovery 页，前端应只消费统一输出，不直接理解：

- RSS family 的内部差异
- ListenBrainz 的 provider 细节
- 后续新增榜单源的特定解析路径

来源差异应止步在后端的输入适配与解析链内部。

## 5. 对当前项目的影响

这条设计基线意味着：

1. 后续不再继续把 `resolution_hints` 作为长期主干模型。
2. `discovery -> metadata` 会从局部 lookup 方案，演进为统一音乐媒体解析链的一个场景。
3. metadata / discovery 的下一轮优化，不应只继续补局部正则或个别 RSS case，而应优先建设统一输入、中间层和正式媒体对象。
4. 新来源接入时，优先做“来源条目 -> MusicMediaInput”的适配，而不是把特定来源规则扩散到前端或多个服务里。

## 6. 当前状态说明

截至当前实现阶段：

- 这条统一音乐媒体解析链已经接管 discovery/detail 主路径
- query builder、subscription execution、organize 已开始消费 `MusicMediaInfo`
- 但 search_job、持久化快照与更多下游场景仍未完成最终收口
- 项目的长期设计方向固定为：

`MusicMediaInput -> MusicMetaBase -> MusicMediaInfo`

后续相关重构、计划、实现与验证，都应以这条基线为准。

## 7. 模块边界

统一音乐媒体解析链后续应拆成以下稳定模块，而不是继续把解析逻辑散落在 provider parser、discovery assembler、metadata lookup 与页面桥接中。

### 7.1 `MusicMediaInputAdapter`

职责：

- 把不同业务场景的原始输入统一映射成 `MusicMediaInput`

典型输入来源：

- discovery 榜单条目
- metadata 搜索输入
- subscription 目标
- acquisition 候选上下文
- organize 上游线索
- 文件路径 / 文件名 / 标签线索

要求：

- 输入适配阶段只做来源收敛，不做最终识别
- 来源差异应止步在这一层，不扩散到页面与下游业务逻辑

### 7.2 `MusicMetaBaseBuilder`

职责：

- `MusicMediaInput -> MusicMetaBase`

应完成的工作：

- 标题、艺人、专辑、发行日期等字段的标准化
- aliases / candidate 归一化
- 外部引用与来源引用归一化
- 证据来源与强度保留

要求：

- 不直接访问前端视图语义
- 不直接承担 provider detail 查询
- 后续 lookup 质量优化优先落在这一层，而不是继续在调用点补局部规则

### 7.3 `MusicMediaRecognizer`

职责：

- `MusicMetaBase -> MusicMediaInfo`

它是统一音乐媒体解析链的核心识别器，内部允许两条路径：

- 强标识直达
- 弱线索识别

但对外只暴露统一识别语义，不把内部路径差异继续抛给调用方。

### 7.4 `MusicMediaInfoHydrator`

职责：

- 基于 `MusicMediaInfo` 继续补齐详情展示所需的富信息

说明：

- `MusicMediaInfo` 是正式媒体对象
- `MetadataDetail` 是它的 detail / hydrated view
- hydrator 只负责补 detail 展示，不反向主导上游识别语义

### 7.5 `MusicMediaChain`

职责：

- 统一编排：
  - `MusicMediaInputAdapter`
  - `MusicMetaBaseBuilder`
  - `MusicMediaRecognizer`
  - `MusicMediaInfoHydrator`

这层是后续最接近 MoviePilot `MediaChain` 设计方法的音乐版编排入口。

要求：

- 各业务场景优先通过这条链获取正式音乐对象
- 不鼓励场景自己跳过链路直接拼 lookup 或 detail 请求

## 7.6 统一 Chain 组织规则

除 `MusicMediaChain` 外，后续凡是以下类型的后端主流程，都应优先实现为独立 `Chain`：

- 下载后整理闭环
- 订阅执行闭环
- 榜单刷新与发现入口主流程
- 其他跨步骤、跨模块、带状态推进的业务链

约束：

- 主流程不再继续用多个 `*Service` 在调用点临时编排
- 调用方优先依赖 `Chain`，而不是直接拼装多个 `Service`
- `Service` 仅保留为 `Chain` 的支撑层，例如 adapter、oper、formatter、provider 访问
- 不为旧目录、旧命名、旧入口保留兼容层；如需重构，优先做激进替换，而不是双轨并存

## 8. 执行流程

统一音乐媒体解析链后续固定为 4 段：

1. `Input Adapt`
2. `Meta Normalize`
3. `Media Recognize`
4. `Detail Hydrate`

### 8.1 Input Adapt

原始来源先进入 `MusicMediaInputAdapter`，转成统一的 `MusicMediaInput`。

目标：

- 保留来源语义
- 剥离页面与来源专有结构
- 为后续中间层构建准备统一输入

### 8.2 Meta Normalize

`MusicMediaInput` 进入 `MusicMetaBaseBuilder`，生成 `MusicMetaBase`。

目标：

- 把原始音乐线索标准化
- 收口 aliases / candidates / source refs / evidence
- 让后续识别围绕统一中间元数据进行

### 8.3 Media Recognize

`MusicMetaBase` 进入 `MusicMediaRecognizer`，生成 `MusicMediaInfo`。

内部路径：

- 如果已具备可靠外部标识，优先走强标识直达
- 如果没有可靠标识，走弱线索识别

但两条路径都必须输出同一种正式媒体对象，而不是形成两套并行主逻辑。

### 8.4 Detail Hydrate

在需要 detail 展示时，由 `MusicMediaInfoHydrator` 把 `MusicMediaInfo` 补成 `MetadataDetail`。

目标：

- 让 detail 成为正式媒体对象的展示视图
- 而不是让 detail 反向承担统一识别的主语义

## 9. 各业务场景的接入方式

### 9.1 discovery

榜单条目进入 detail、订阅或后续搜索前，先转成 `MusicMediaInput`，再进入统一链。

这意味着：

- discovery 不再继续维护长期有效的局部 lookup hints 主路径
- RSS、ListenBrainz 与后续榜单源，都优先做“来源条目 -> MusicMediaInput”适配

### 9.2 metadata detail

detail 本身不是独立识别体系，而是统一链的一个消费场景：

- 输入先统一进入 `MusicMediaInput`
- 再构造成 `MusicMetaBase`
- 再识别成 `MusicMediaInfo`
- 最后 hydrate 成 `MetadataDetail`

### 9.3 search

搜索前的实体确认应优先复用：

- `MusicMetaBase`
- `MusicMediaInfo`

而不是继续在 QueryBuilder 或调用点里独立重复实体判断。

### 9.4 subscription

订阅目标保存与执行时，应优先保存或复用统一音乐实体语义，而不是长期依赖场景私有 target 结构。

### 9.5 acquisition / dispatch

获取链路在进入搜索候选、派发下载与 path handoff 之前，应尽量以统一正式音乐对象为上游实体确认来源。

### 9.6 organize

organize 上游当前已有本地 metadata 识别能力；后续应逐步与统一音乐媒体解析链收敛，而不是长期保持独立演化。

## 10. 当前不建议继续强化的旧路径

在统一音乐媒体解析链正式落地前，以下路径应被明确视为过渡态：

- `DiscoveryTarget` 长期承载主干识别语义
- `resolution_hints` 继续向更多来源扩散
- 页面直接消费来源特判
- 多个业务模块各自维护独立 lookup 逻辑

这些路径可以作为过渡实现保留到正式重构开始，但不应再被当作长期设计继续强化。

## 11. 与现有代码的对接边界

统一音乐媒体解析链的重构目标，不是推翻现有 provider、宿主接口语义或前端页面，而是把“上游实体识别”重新收口。

### 11.1 当前应被重构吸收的路径

后续应逐步被统一链吸收的现有路径包括：

- discovery 中的 `DiscoveryTarget` 主干识别语义
- RSS family parser 输出的长期 hints 主路径
- `/metadata/lookup` 当前面向来源特判的 lookup 组织方式
- QueryBuilder 中重复的上游实体判断
- organize 上游与 metadata/detail 彼此独立演化的识别路径

### 11.2 当前不应被重构推翻的路径

以下内容在这次上层统一重构中保持稳定：

- 宿主 HTTP API 语义与当前固定调用规则
- downloader runtime / path handoff / organize preview/apply 的底层边界
- metadata provider 自身的搜索、详情、缓存能力
- chart provider 自身的取数、缓存和来源适配能力
- 插件中心页面、dashboard、侧边栏导航和独立页面入口

也就是说，这次重构的核心是“上游识别语义统一”，不是重新打开宿主适配或 UI 入口改造。

### 11.3 `/metadata/lookup` 的处理结论

`/metadata/lookup` 不再保留，也不再演进。

处理结论固定为：

- 旧 `/metadata/lookup` 路由直接删除
- discovery/detail/search/subscription/organize 不再通过它进入统一链
- 对外统一入口只保留：
  - `/media/prepare`
  - `/media/resolve`
  - `/media/resolve/detail`

## 12. 统一诊断与错误语义

统一音乐媒体解析链不能只返回“命中”或“未命中”，还必须能回答失败发生在哪一段。

### 12.1 诊断分段

后续诊断至少应区分：

- `input_invalid`
- `input_insufficient`
- `meta_normalized_with_warnings`
- `strong_ref_unresolved`
- `recognition_not_found`
- `recognition_ambiguous`
- `provider_unavailable`
- `detail_hydration_failed`

### 12.2 诊断归属

诊断信息应尽量归属到统一链的固定阶段：

- `MusicMediaInputAdapter`
- `MusicMetaBaseBuilder`
- `MusicMediaRecognizer`
- `MusicMediaInfoHydrator`

这样后续调试时能明确区分：

- 是来源输入不足
- 是中间元数据标准化不够
- 是 provider 识别没有命中
- 还是 detail 补全失败

### 12.3 证据保留

`MusicMetaBase` 与 `MusicMediaInfo` 后续都应保留最小必要证据与诊断摘要，用于：

- 运行态调试
- 命中质量回归
- 前端最小可解释状态展示

但页面不应直接消费来源原始 payload 作为主诊断语义。

## 13. 验证与完成定义

统一音乐媒体解析链不是写出模型名就算完成，后续应按场景完成验证。

### 13.1 最小验证场景

至少应覆盖：

- discovery 条目 -> detail
- 搜索输入 -> 统一识别
- subscription 目标 -> 统一识别
- organize 上游线索 -> 统一识别

### 13.2 命中质量验证

后续回归集不再只围绕单个 parser 或 lookup case，而应围绕统一链验证：

- 输入是否正确收敛成 `MusicMediaInput`
- 是否正确构造成 `MusicMetaBase`
- 是否正确识别成 `MusicMediaInfo`
- 失败时诊断是否落在正确阶段

### 13.3 完成定义

当以下条件成立时，可认为统一音乐媒体解析链已经成为项目正式基线而不再只是设计基线：

- discovery/detail/search/subscription/organize 上游识别均已接入统一链
- 旧的 `resolution_hints` 主路径已不再作为长期主干
- 命中质量优化开始围绕统一中间层和正式媒体对象推进
- 文档、测试与运行态验证都以统一链为主语义，而不是以过渡态 lookup 为主语义

## 14. 字段级模型定义

本节给出后续彻底重构时应采用的字段级模型基线。字段设计优先追求长期稳定、可扩展和与 MoviePilot 设计方法一致的分层，而不是为兼容当前过渡态接口让步。

### 14.1 `MusicMediaInput`

用途：

- 表达某个业务场景拿到的原始音乐线索
- 作为统一音乐媒体解析链的唯一外部输入对象

建议字段：

- `entity_hint`
  - `artist | album | track | unknown`
- `source_kind`
  - `discovery | detail | search | subscription | acquisition | organize | library | manual`
- `title`
- `subtitle`
- `artist_names`
- `album_title`
- `album_artist_names`
- `release_date`
- `year`
- `track_number`
- `disc_number`
- `external_refs`
- `source_context`
- `raw_context`

设计要求：

- 保留来源信息，但不在这层做最终实体判断
- 不将页面展示字段与运行时动作字段混入主模型

### 14.2 `MusicMetaBase`

用途：

- 统一承接标准化之后、正式识别之前的音乐元数据

建议字段：

- `entity_type`
- `canonical_title`
- `canonical_artist_names`
- `canonical_album_title`
- `canonical_album_artist_names`
- `canonical_release_date`
- `canonical_year`
- `track_number`
- `disc_number`
- `alias_titles`
- `alias_artist_names`
- `alias_album_titles`
- `featuring_artist_names`
- `external_refs`
- `source_refs`
- `evidence`
- `normalization_notes`
- `confidence_hint`

设计要求：

- 这是统一识别输入，不是前端 detail 或 provider 响应
- 当前 RSS title/artist/album candidates 之类的能力，后续应内化到这层，而不是继续长期以散落 hints 形式存在

### 14.3 `MusicMediaInfo`

用途：

- 统一承接正式识别后的音乐实体对象

建议字段：

- `entity_type`
- `provider`
- `provider_id`
- `title`
- `artist_names`
- `album_title`
- `album_artist_names`
- `release_date`
- `year`
- `track_number`
- `disc_number`
- `related_artist_ids`
- `related_album_id`
- `related_track_ids`
- `external_refs`
- `match_confidence`
- `match_strategy`
- `match_evidence`
- `diagnostics`
- `cover_url`
- `disambiguation`
- `release_context`

设计要求：

- 后续 search、subscription、acquisition、organize 上游确认，尽量直接复用这一层
- `MetadataDetail` 更适合作为 `MusicMediaInfo` 的 detail/hydrated view，而不是反过来主导识别链

## 15. 统一链 API 边界

统一音乐媒体解析链后续应暴露清晰的链路 API，而不是继续让多个模块直接拼 lookup。

### 15.1 主公共入口

建议后续统一对外暴露一条主入口：

- `MusicMediaChain.resolve(input: MusicMediaInput) -> MusicMediaInfo`

在需要详情时，再由：

- `MusicMediaChain.resolve_detail(input: MusicMediaInput) -> MetadataDetail`

或等价编排入口继续向下 hydrate。

### 15.2 场景适配入口

各业务场景不应自己拼装最终识别逻辑，而应只负责提供自己的输入适配器，例如：

- `from_discovery_entry(...) -> MusicMediaInput`
- `from_search_request(...) -> MusicMediaInput`
- `from_subscription_target(...) -> MusicMediaInput`
- `from_organize_context(...) -> MusicMediaInput`

这层只负责来源收口，不负责最终识别。

### 15.3 `/metadata/lookup` 的替换结论

后续不再强化、保留或复用 `/metadata/lookup`。

旧的：

- `entity_type + hints dict -> metadata detail`

已经属于应删除对象。

统一链对外只保留：

- `POST /media/prepare`
- `POST /media/resolve`
- `POST /media/resolve/detail`

1. discovery 下钻 detail 已不再依赖 `DiscoveryTarget + resolution_hints`
2. `/metadata/lookup` 已被删除，不再作为统一音乐媒体解析链的任何 HTTP 投影
3. 前端不再理解 `direct_id / search_lookup` 模式
4. search、subscription、organize 上游开始复用 `MusicMetaBase` 或 `MusicMediaInfo`
5. 命中质量优化不再以 family-specific hints 为主干，而是以统一中间元数据和统一正式媒体对象为主干

## 18. 持久化与缓存边界

统一音乐媒体解析链后续不应把所有中间对象都机械落库，而应按职责决定哪些是瞬时对象、哪些是快照对象、哪些是缓存对象。

### 18.1 `MusicMediaInput`

默认视为瞬时对象。

原则：

- 用于单次请求、单次场景进入统一链
- 不作为长期数据库主模型持久化
- 如需追踪来源，仅在运行摘要、调试日志或任务快照里保留最小输入摘要

### 18.2 `MusicMetaBase`

默认视为统一链内部的中间对象。

原则：

- 不应成为新的业务主表
- 在需要调试、回归或长链路可追溯时，可作为快照保留在：
  - subscription run 摘要
  - search job 摘要
  - organize record 摘要
- 快照应保留“最小必要字段 + 证据摘要”，而不是把原始 payload 整体塞进数据库

### 18.3 `MusicMediaInfo`

这是后续最适合被业务快照复用的正式对象。

原则：

- 订阅目标、搜索目标、organize 上游目标、获取链路目标，后续应优先保存 `MusicMediaInfo` 的快照，而不是继续保存零散 target payload
- 这些快照用于：
  - run 回放
  - 诊断
  - 下游 search / dispatch / organize 复用

### 18.4 缓存策略

缓存边界应保持在两个层次：

1. provider 缓存
   - 继续保留在 metadata/chart provider 层
2. 统一链识别缓存
   - 如后续需要新增，只应缓存：
     - `MusicMetaBase` 指纹 -> `MusicMediaInfo`

不建议：

- 缓存原始 `MusicMediaInput`
- 缓存页面专用视图对象
- 继续以来源特定 hints 作为缓存 key 主语义

## 19. API 收口方向

统一音乐媒体解析链落地后，当前 API 也应随之收口，而不是继续让多个入口各自维护自己的识别语义。

### 19.1 内部服务 API

后续建议内部统一只保留：

- `MusicMediaChain.resolve(input: MusicMediaInput) -> MusicMediaInfo`
- `MusicMediaChain.resolve_detail(input: MusicMediaInput) -> MetadataDetail`

如果某些场景只需要中间层调试能力，可以提供内部辅助入口，但不作为页面或外部主入口。

### 19.2 HTTP API

后续建议的外部 HTTP 语义应是：

- `POST /media/resolve`
- `POST /media/resolve/detail`

或等价命名的统一媒体解析入口。

这比继续保留任何“面向 hints 的 `/metadata/lookup`”残影更符合统一音乐媒体解析链语义。

### 19.3 现有 API 的处理原则

- `/metadata/search`、`/metadata/{entity}/{id}` 这类 provider/search/detail API 仍可保留
- 但“从非稳定实体线索进入识别”的职责只由统一媒体解析入口承担，不再借道 `/metadata/lookup`

也就是说：

- provider detail API 继续存在
- 统一媒体解析链 API 成为 discovery / search / subscription / organize 上游识别的正式入口

## 20. 代码组织重构方向

为了避免这次重构只停留在模型层，后续代码组织也应明确收口。

### 20.1 新增的主服务模块

后续建议新增或明确的主服务模块包括：

- `backend/app/services/music_media_chain.py`
- `backend/app/services/music_media_input.py`
- `backend/app/services/music_meta_base.py`
- `backend/app/services/music_media_recognizer.py`

命名可以微调，但职责不应再次混入 discovery、metadata 页面桥接或 provider parser。

### 20.2 现有模块的角色变化

- `discovery.py`
  - 从“兼顾展示 + 解析桥接”
  - 收缩为“产品化 discovery 视图装配”
- `metadata.py`
  - 从“既做 provider detail，又做 lookup 桥接”
  - 收缩为“metadata provider/search/detail 服务”
- `rss_feed_parser.py`
  - 从“长期 hints 主干生产者”
  - 收缩为“来源条目结构化解析器”

### 20.3 前端组织变化

前端后续应只保留：

- discovery 展示逻辑
- 调用统一媒体解析入口打开 detail

不再保留：

- `DiscoveryTarget` 作为前端主类型
- `direct_id / search_lookup` 模式判断
- 来源 family 的前端识别逻辑

## 21. 彻底重构约束

这次设计默认接受 breaking change，因此后续实现时应明确遵守：

- 不保留新旧 discovery 契约双轨并行
- 不为旧的 `DiscoveryTarget` / `resolution_hints` 设计兼容层
- 不要求旧前端类型继续可用
- 如有需要，数据库和本地开发状态可直接重建

这不是一次增量修补，而是统一音乐媒体解析链的一次性全局替换。
