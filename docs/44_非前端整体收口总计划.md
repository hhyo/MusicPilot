# 非前端整体收口总计划

> 状态：2026-04-13 制定。本文覆盖除前端重写之外的全部剩余目标，用作统一执行与验收基线。

## 1. 结论

截至当前版本，以下部分已经可以视为“主干完成”：

- 统一音乐媒体解析链：`MusicMediaInput -> MusicMetaBase -> MusicMediaInfo`
- metadata / charts / jobs / downloads / organize / subscriptions / settings / dashboard 主业务 API
- plugin runtime backend mirror
- 基础测试、打包、README / backend README 主说明

但如果按最终产品目标“发现 -> 识别 -> 获取 -> 下载 -> 整理 -> 订阅自动化 -> 宿主联调可信交付”衡量，**除前端外仍未全部完成**。

当前剩余工作不再是大架构重构，而是以下 5 个产品化里程碑：

1. 获取链路产品化与命中质量收口
2. 下载完成后的自动闭环
3. 生产级调度与后台任务
4. 宿主能力验证与 probe 收口
5. 运行态观测、诊断与交付真相

## 2. 本计划的范围

### 2.1 在范围内

- metadata / discovery / acquisition 命中质量
- QueryBuilder、SearchJob、dispatch、downloads workspace 的产品化补齐
- path handoff、下载完成回填、自动 organize / apply 的闭环收口
- subscription scheduler 与后台任务能力增强
- host probe / validation / diagnostics 的真实化收口
- dashboard 与运行态观测增强
- 文档、测试、runtime mirror、打包与运行态验证

### 2.2 不在范围内

- 前端视觉、页面结构、组件体系重写
- 新 metadata provider
- 新 chart provider / 新 discovery 源
- 宿主 MoviePilot / MoviePilot-Frontend 代码改造
- 数据库体系重构或引入消息队列、中间件基础设施

## 3. 最终完成定义

只有同时满足以下条件，才可认为“除前端外，整体目标达成”：

1. 统一音乐媒体解析链不再有待收口的主路径问题。
2. QueryBuilder / SearchJob / dispatch / downloads workspace / organize / subscription execution 串成稳定的后端业务闭环。
3. 下载完成后的 path handoff、自动 organize preview、自动 apply 具备明确状态机和恢复动作。
4. scheduler 不再只是最小 polling demo，而具备幂等、retry、run 管理和后台任务边界。
5. probe 不再只是大量 placeholder/unverified 的壳层，而形成真实宿主能力结论与诊断输出。
6. dashboard 能表达 provider、discovery、search、downloads、handoff、organize、scheduler 的真实状态。
7. README、backend README、路线文档与运行态文档都能如实反映当前状态。
8. backend 全量测试、关键定向测试、plugin_runtime 打包、必要的真实运行态验证全部通过。

  - detail 仍只停留在 metadata 结果，不包含获取、派发、整理上下文
- `backend/app/services/music_media_recognizer.py`
  - 命中质量与去歧义仍可继续提升

### 4.2 下载闭环问题

- `backend/app/services/pending_handoff.py`
  - 已有自动续跑，但需要与下载工作台、scheduler、diagnostics 更紧密耦合

### 4.3 调度与后台任务问题

- `backend/app/services/subscription_scheduler.py`
  - 当前仍是 in-process minimal scheduler
- `backend/app/tasks/__init__.py`
  - 明确还是 placeholder 级后台任务边界

### 4.4 宿主验证问题

- `backend/app/api/routes/probe.py`
- `backend/app/adapters/host_probe.py`
  - 仍保留大量 `placeholder / unverified / degraded`
  - notify / config / sites / downloader / search / dispatch 的真实宿主字段映射仍未完全收口

### 4.5 交付与可观测性问题

- `backend/app/services/dashboard.py`
  - 已是聚合接口，但仍偏摘要，不足以支撑完整产品诊断
- 文档虽然已较真实，但仍需要在“完成态”下再做一次统一收口

## 5. 一次性并行工作流

### Workstream A：Metadata / Discovery / Acquisition 命中质量

**目标**

- 把“能跑”提升到“命中质量稳定、诊断清晰”。

**处理项**

- 强化 `MusicMetaBaseBuilder` 的归一化能力
- 强化 `MusicMediaRecognizer` 的评分与去歧义
- 提升 RSS / 弱来源 discovery 条目的命中质量
- 让 `QueryBuilder` 直接围绕 `MusicMediaInfo` 提供更可执行的查询结构
- 为获取链路补真实回归样本集

**完成定义**

- 真实弱来源样本集有稳定回归测试
- 同名 track / 多艺人 / 版本噪声去歧义稳定
- 查询结构对真实 PT 搜索环境的适配性有明确验证样本

### Workstream B：SearchJob / Candidate / Dispatch / Downloads Workspace 完整化

**目标**

- 把获取工作台真正做成可管理业务面，而不是只停在单次执行。

**处理项**

- 完善 candidate confirm/reject 后的状态传播
- 完善 job cancel / retry / delete 后的行为约束与错误语义
- 完善 downloads tasks 与 bindings 的关联展示字段
- 增加 dispatch 失败、retry-dispatch、retry-handoff 的诊断输出
- 明确 downloader task、binding、search job、organize record 的关系链

**完成定义**

- jobs 与 downloads workspace 都能独立支撑“查看 -> 决策 -> 重试 -> 恢复”
- 关键状态都有统一语义，不再只是工程字段拼接

### Workstream C：下载完成后的自动闭环

**目标**

- 把 `dispatch -> handoff -> organize preview/apply` 收成真正稳定的自动链路。

**处理项**

- 强化 `pending_handoff` 处理与 scheduler 的联动
- 明确 handoff 状态机：
  - pending
  - resolved
  - unresolved
  - failed
- 加强自动 preview / apply 的触发条件与失败恢复动作
- 为 handoff unresolved、path 缺失、organize apply 失败补结构化诊断
- 为 downloads workspace 与 dashboard 暴露 handoff 恢复状态

**完成定义**

- 下载完成后的自动闭环有稳定状态机和恢复动作
- 失败不会静默，只会进入明确可观测状态

### Workstream D：Subscription Scheduler 与后台任务产品化

**目标**

- 把当前最小 scheduler 提升到产品可用层级。

**处理项**

- scheduler run 结果、reason_counts、diagnostics 继续强化
- 增加 run retry、preview_only、dry-run 语义的统一约束
- 补齐幂等、重复运行保护、运行窗口和重试策略
- 定义后台任务边界，收掉 `backend/app/tasks/__init__.py` 的 placeholder 表述
- 让 scheduler / pending handoff / organize 恢复动作进入统一后台任务语义

**完成定义**

- scheduler 不再只是 polling demo
- 后台任务边界清晰，且文档、代码、测试一致

### Workstream E：Host Probe / Validation / Diagnostics 收口

**目标**

- 让 probe 成为真实可用的宿主能力验证层，而不是大量保守占位返回。

**处理项**

- 清理 probe 路由的 TODO 文案
- 收紧 `host_probe` 的 mock / real / degraded 判断边界
- 为 notify、config、sites、downloaders、search、dispatch 逐项形成真实字段映射结论
- 收紧 `unverified` 与 `placeholder` 的使用范围，仅保留真正未确认的宿主边界
- 让 validation matrix 与 probe 输出互相印证

**完成定义**

- probe 不再是“默认占位解释接口”
- 宿主能力的未完成项被压缩到最小边界

### Workstream F：Dashboard / 运行态观测 / 文档真相

**目标**

- 让后端真正可观测、可交付，而不是只能跑通。

**处理项**

- dashboard 增加更细的 diagnostics 维度
- 汇总 provider/discovery/search/downloads/handoff/organize/scheduler 状态
- 补充运行态验证文档
- 最终同步：
  - `README.md`
  - `backend/README.md`
  - `docs/28_项目整体任务盘点与执行路线.md`
  - 新增或更新运行态验证文档

**完成定义**

- 文档、dashboard、probe、后端状态表达一致
- 新维护者不需要读实现也能知道当前真实完成边界

## 6. 执行方式

本计划不再按单线顺序推进，而按以下方式执行：

- 使用独立 worktree
- 非前端范围内并行推进多个工作流
- 每条工作流都要求：
  - 先补测试
  - 再做实现
  - 再跑定向验证
- 所有工作流最后统一回到主线：
  - backend 全量测试
  - 打包
  - 文档同步
  - 必要的真实运行态验证

## 7. 禁止回摆项

在本计划执行期间，不允许再出现以下回摆：

- 不再回到“先做一点 API，再分析还缺什么”的方式
- 不再重新引入统一音乐媒体解析链之外的新识别主路径
- 不再用 placeholder 文案掩盖主业务未完成
- 不再把 probe/mock/stub 成功表述成真实宿主成功
- 不再把“后面再补”当作完成结论

只有在以下判断都成立时，才能输出“除前端外整体目标达成”：

- 后端主链完整
- 获取链路完整
- 自动闭环完整
- 调度与后台任务达到产品可用层级
- probe / diagnostics / dashboard 能支撑真实交付
- 文档与运行态真相一致

否则只能说：

- “主干已完成”
或
- “后端已可支撑前端开发”

不能说整体目标已经达成。
