# 28. 项目整体任务盘点与执行路线

## 目标

在 `organize preview/apply` 已完成音乐语义收口与真实宿主插件 API 验证之后，重新梳理 MusicPilot 的整体目标、当前进展与后续执行顺序，避免项目继续围绕单一模块局部推进。

本文件回答三件事：

1. 当前项目已经完成到什么程度。
2. 除文件整理以外，还剩哪些关键任务。
3. 接下来应该按什么顺序推进，才能最接近“完整音乐业务闭环”。

## 当前基线判断

### 已完成并可进入维护态的部分

以下能力已经从“概念验证”提升到“当前版本可用”，后续只做必要修补，不再作为第一优先级深挖：

- 插件壳层、插件 API 命名空间、运行时打包与本地宿主真实加载
- 宿主插件中心 `vue` 远程组件页面入口
- metadata 搜索、QueryBuilder、SearchJob、候选评分、下载绑定与 organize record 基础落库
- host integration 的固定接口语义收口
- path handoff 的固定来源定义
- `organize preview` 本地音乐路径预览
- `organize apply` 音乐路径规划 + 宿主底层文件/存储执行
- 真实宿主插件 API 下的最小音乐 `preview_ready -> applied` 成功闭环
- 带嵌入标签的真实音乐样本 `preview -> apply` 闭环

这意味着：

- `organize` 目前已经不再是项目主阻塞
- 后续若继续投入 `organize`，应以增强 metadata/layout 能力为主，而不是继续改执行桥接

### 仍明显未完成的主需求

对照最初的业务目标“发现 -> 搜索 -> 订阅 -> PT 获取 -> 下载 -> 整理入库”，当前还缺的是：

- 真实音乐元数据源接入
- 真实榜单发现源接入
- 订阅从“手动 run”升级到“自动调度”
- 下载完成后的自动进入 organize
- 真实获取链路的产品级闭环与验收
- 设置、诊断、发布文档的交付收口

## 当前模块状态盘点

### A. 已成型模块

#### 0. settings

当前实现：

- `/settings` 已从 placeholder 变成最小可用设置页
- `/settings/providers` 已从 placeholder 变成真实读写接口
- chart provider 运行时优先读取项目 settings，环境变量仅作为 fallback

结论：

- settings 的主链配置入口已经可用，后续优先补完整的设置项语义和更细的运行态校验，而不是继续停留在占位页

#### 1. organize

- 上层已经拆成：
  - `music_metadata.py`
  - `music_layout.py`
  - `organize_strategy.py`
- 预览与执行语义已对齐音乐业务，而不是影视语义。
- 真实宿主插件 API 闭环已验证通过。

结论：

- `organize` 进入维护态
- 后续只做 metadata/layout 增强，不再作为总路线的第一主战场

#### 2. 插件正式化

- `plugin_runtime` 已能被本地宿主真实加载
- 宿主插件中心已能真实打开 MusicPilot 页面
- 真实插件 API 可访问
- 真实插件内 file/storage 执行已验证

结论：

- 插件 formalization 主阻塞已解除

### B. 仍处于 MVP / 占位阶段的模块

#### 1. metadata provider

当前实现：

- `backend/app/adapters/metadata_provider.py`
- 当前已具备 `seed` 与 `MusicBrainz` 两种模式

问题：

- 真实 provider 目前只覆盖 Artist / Album / Track 搜索与详情
- provider 输出已具备第一阶段 TTL 缓存
- 还没有 provider 配置持久化和多源聚合
- 当前订阅目标与 discovery 仍有不少 seed/local 依赖

影响：

- 上游实体发现与 metadata 可信度不够
- 后续下载、整理和订阅命中质量都会受限

#### 2. charts / discovery

当前实现：

- `backend/app/adapters/chart_provider.py`
- `backend/app/services/charts.py`
- 当前已具备 `mock`、`listenbrainz` 与 `rss_feed` 三种模式

问题：

- 第一版真实榜单只覆盖 ListenBrainz sitewide artists / recordings
- `rss_feed` 已通过 settings 配置进入真实 discovery，当前验证样本至少包括网易云热歌榜 playlist RSS、YouTube TopSongs RSS、YouTube TopArtists RSS；`item_count` 分别可写为 `200`、`100`、`100`
- provider 输出已具备第一阶段 TTL 缓存
- discovery detail 已具备第一轮产品化视图与稳定 `DiscoveryTarget` 转化层：非 RSS 走 `direct_id`，RSS 走 `search_lookup` + `/metadata/lookup`，榜单条目点击会进入 metadata drawer
- 在 `metadata provider mode=seed` 的运行态下，示例 lookup 可能返回“未匹配到 metadata”，这说明当前 metadata 结果未命中，而不是 discovery 接口缺失
- 还没有复杂 RSS 可视化 CRUD、真实专辑榜、增量发现、差异命中与自动刷新

影响：

- “发现”入口已经从纯 mock 进入真实阶段，且完成了 RSS -> metadata lookup 的第一轮闭环；但当前仍以 settings 驱动的最小发现闭环为主，复杂 RSS 可视化 CRUD 还未进入本轮范围

#### 3. subscriptions / scheduler

当前实现：

- `subscriptions/{id}/run` 为同步最小执行骨架
- 应用内已具备最小 polling scheduler，可按 `schedule_interval_minutes` 自动触发 due subscription
- schema 里仍保留 `scheduled_placeholder` 兼容旧数据，但运行时统一归一为 `scheduled`
- 最佳 `AUTO_DOWNLOAD` 候选已可在 run 内继续自动 dispatch，并生成 binding-based organize preview

问题：

- 还没有 cron 级配置能力
- 没有幂等、失败重试、自动 run 管理
- 调度仍是单进程、应用内 polling，不是独立任务系统

影响：

- 订阅页已经从“纯手动入口”进入最小自动化阶段，但离产品级订阅系统仍有明显距离

#### 4. acquisition / dispatch 主链

当前实现：

- SearchJob、评分、dispatch 都有后端能力
- `subscription run` 已能从 metadata -> search -> auto dispatch(best candidate) -> organize preview 走到第一版自动闭环
- 当 preview 已具备明确本地源文件时，同一条执行链已可继续自动 apply
- 真实宿主插件 API 下，默认 `seed + mock search/dispatch` 运行态已验证可走到 `dispatched + preview_ready`
- 真实宿主插件 API 下，`plugin runtime` 已能自动派生 host 默认值并启用 `real_host_search`
- 真实宿主插件 API 下，Adele 基准样本已验证 `real_host_search` 可返回真实候选
- 真实宿主插件 API 下，`MusicBrainz metadata + ListenBrainz track chart entry` 已验证可进入 `subscription -> run`，但当前首个 BTS 样本停在 `no_result`
- `QueryBuilderService` 已完成一轮 PT 友好查询优化，track/album 的前 4 条查询已优先对齐 `artist + title/album + format` 这类常见 release title 形态
- 真实宿主插件 API 下，Adele 基准 track 订阅 run 已验证会进入真实 `dispatch`，并通过宿主 downloader runtime 真正创建下载任务
- 相同样本重复 run 时，当前已能稳定复用既有 qB 任务，不再把“已存在任务”误报成失败

问题：

- 真实 PT 搜索与音乐匹配还不是生产级闭环，部分真实 track 样本仍无候选
- 当前宿主运行态虽然已经有下载器，但真实 acquisition 仍受两类因素限制：
  - 部分真实 discovery 样本在当前 PT 站点环境下仍搜不到结果
  - 下载完成后的自动 path handoff / 自动 organize / 自动 apply 仍未形成系统化流程

影响：

- 项目级闭环已从“真实上游 + mock acquisition”推进到“真实上游 + 真实 search 已验证 + 真实 music dispatch 已通过 downloader runtime 创建下载任务”的阶段

#### 5. frontend / docs 状态真相

当前实现：

- 前端页面已具备最小壳层
- 但很多文案仍停留在 “Phase 6 / mock chart / skeleton” 时代

问题：

- README、backend README、前端 phase 文案与当前真实实现存在滞后

影响：

- 项目理解成本高
- 外部维护者容易误判当前真实能力边界

## 新的执行原则

从当前阶段开始，项目应遵守以下路线原则：

1. **停止围绕 organize 内部继续深挖执行桥接。**
   organize 已经具备闭环能力，除 metadata/layout 增强外，不再作为主轴。

2. **优先补上游真实数据能力。**
   如果 metadata 与 discovery 还停留在 mock，后续所有自动化闭环都只能是半成品；当前 settings 驱动的 RSS discovery 已经进入真实运行态，但 metadata lookup 仍要继续收敛。

3. **优先做“主链完成度”，不是继续堆模块。**
   下一阶段的目标应是让：
   - metadata
   - discovery
   - subscription
   - acquisition
   - organize
   真正串成可运行产品链，而不是每个模块各自可演示。

4. **先做真相收口，再做功能扩张。**
   当前文档、前端状态标签和 README 需要先同步到当前真实状态，否则越做越乱。

## 重新规划后的执行顺序

### Phase A：项目状态真相收口

#### 目标

把 README、backend README、前端 phase 文案、模块说明更新到当前真实状态。

#### 重点

- 清掉前端仍残留的 `Phase 6 / mock-only / skeleton` 旧表述
- 更新首页、模块卡片、placeholder 文案
- 更新 README / backend README / docs 中对 preview/apply、plugin runtime、真实闭环能力的描述
- 收口 `/settings`、`/settings/providers` 和 RSS discovery 的真实运行态表述

#### 完成定义

- 仓库文本与当前真实实现一致
- 新维护者只看 README 和首页，也能知道当前真实能力边界

---

### Phase B：真实音乐元数据源接入

#### 目标

把 `metadata` 从本地 seed 提升为真实 provider 驱动，并保留 seed 作为 fallback 或开发数据。

#### 重点

- 实现真实 `MetadataProviderAdapter`
- 保留当前 `MusicMetadataRecognizer` 作为 organize 的本地识别层
- 不混淆“搜索元数据源”和“文件整理恢复元数据”的职责

#### 为什么现在做

- metadata 是 discovery、subscription、query builder、organize 的共同上游
- 不先做这一层，后面的自动闭环都会缺真实输入

#### 完成定义

- Artist / Album / Track 搜索和详情可来自真实 provider
- 当前前端搜索页不再只依赖 seed catalog
- 第一阶段实现可先只接入单一真实源，后续再做缓存与 provider 扩展

---

### Phase C：真实榜单发现源接入

#### 目标

把 `charts` 从单一真实源提升为更完整的真实榜单发现入口。

#### 重点

- 扩展真实 chart provider
- 定义榜单快照与条目映射
- 保持当前 chart -> subscription 创建动作不变

#### 为什么现在做

- “发现”是产品闭环上游
- 榜单订阅如果一直停留在 mock，订阅系统就无法转为真实业务流

#### 完成定义

- 榜单列表、详情、条目来自真实源
- 当前 RSS discovery 已经能通过 settings 真实进入运行态，后续再扩展更多榜单源、刷新与交互能力

---

### Phase D：订阅调度与自动执行

#### 目标

把 `subscription` 从“手动 run”升级到“真实自动调度”。

#### 重点

- 调度器接入
- run 幂等
- 失败重试
- 最新 run 状态与异常可追踪

#### 为什么现在做

- 没有自动调度，订阅就只是手工按钮，不是订阅系统

#### 完成定义

- 订阅可自动触发 run
- run 状态、失败、重试可回看

---

### Phase E：获取->下载->整理自动闭环

#### 目标

把 acquisition / dispatch / organize 串成真实自动闭环。

#### 重点

- SearchJob 命中后自动决策派发
- 下载完成后稳定进入 organize
- path handoff / organize record 回写与订阅 run 状态贯通

#### 为什么现在做

- 这是项目最核心的产品闭环
- 前面 Phase B/C/D 完成后，这一步才真正有稳定上游输入

#### 完成定义

- 一个真实目标可从发现或订阅触发，最终进入下载并整理成功
- 端到端状态可回看

---

### Phase F：设置、诊断、发布收口

#### 目标

把当前系统从“开发态可跑”收成“可交付插件”。

#### 重点

- 设置页补全
- 运行态诊断与错误说明
- 安装、升级、重建、发布说明
- plugin_runtime / package 输出收口

#### 完成定义

- 有清晰安装与升级路径
- 有完整运维和验证文档
- 可交付给外部使用者复现

## 当前推荐的下一阶段主线

最推荐的下一步不是继续增强 organize，而是：

1. **先做 Phase A：项目状态真相收口**
2. **立刻进入 Phase B：真实音乐元数据源接入**

原因：

- 这两步是当前收益最高、依赖最少、对整体主链帮助最大的工作
- 它们能直接抬高搜索、订阅、发现、下载、整理四条链路的真实性

## 不建议现在优先做的事

以下事项当前不应作为主优先级：

- 继续深挖 `organize apply` 内部执行细节
- 再次扩展影视语义宿主链路
- 提前做复杂推荐系统或策略系统
- 提前做播放、社交热度、推荐算法
- 在 metadata 和 discovery 仍是 mock 时就拼命做调度器细节
- 本轮不做复杂 RSS 可视化 CRUD

## 最终判断

当前 MusicPilot 项目已经完成了：

- 插件正式化
- organize 音乐语义收口
- 最小真实闭环验证

但距离“完整音乐业务闭环”还差 4 块核心能力：

1. 真实 metadata
2. 真实 discovery
3. 自动 subscription run
4. acquisition -> dispatch -> organize 自动闭环

因此，后续执行应明确从“整理模块建设期”切换到“主链完成期”。
