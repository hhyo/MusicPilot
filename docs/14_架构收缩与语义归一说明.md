# 14. 架构收缩与语义归一说明

> 用途：说明 MusicPilot 当前轮的收缩结果。本文不再讨论 recommendation / strategy / matrix 驱动，而是只说明固定接口语义、固定场景调用规则、单一权威数据来源，以及已经删除或收敛的过度抽象。

## 14.1 当前最小架构

MusicPilot 当前实现收缩为三层：

1. 接口语义层
   - 明确每个 MoviePilot 宿主接口做什么、入参是什么、返回什么、成功和失败分别表示什么。
2. 场景调用层
   - 每个 MusicPilot 场景只对应一个主调用语义。
   - 如确实存在两个接口，也把它们定义成两个不同语义，而不是运行时 fallback。
3. 数据来源层
   - 每个关键字段只定义一个权威来源。
   - 需要补充来源时，也明确写成“补充/历史重放来源”，而不是通用 fallback 引擎。

另外，后端主业务流程的组织方式固定收敛为 MoviePilot 风格的 `Chain`：

4. 主流程编排层
   - 跨步骤、跨模块、带状态推进的后端主链路统一由 `*Chain` 编排。
   - `Service` 只保留为 `Chain` 的支撑层，不再承担主流程编排职责。
   - 目标目录结构与命名方式也向 MoviePilot 对齐：
     - `api/endpoints`
     - `chain`
     - `db/models`
     - `db/*_oper.py`
     - `helper`
     - `modules`
   - `api/routes`、`services`、`models`、`repositories`、`adapters` 不再作为长期主结构保留。

## 14.2 宿主接口语义

| 宿主接口 | 确定语义 | 适合的输入场景 | 关键返回字段 | 成功/失败语义 |
|---|---|---|---|---|
| `/api/v1/search/title` | 按标题关键词搜索候选资源 | 只有标题、年份、别名等文本线索时 | `Response.success`、`data[]`、`Context.torrent_info` | 成功表示宿主按 title 语义完成搜索；失败就是 title 语义失败 |
| `/api/v1/search/media/{mediaid}` | 按宿主可识别 media id 精确搜索 | 已有可靠宿主媒体 ID 时 | `Response.success`、`data[]`、`Context.torrent_info` | 成功表示按 media 语义完成搜索；失败不再自动切 title search |
| `/api/v1/download/` | 用已识别 `media_in` + `torrent_in` 发起下载 | candidate 已能构造可靠 `media_in` | `Response.success`、`data.download_id` | 成功表示宿主接受“已识别媒体下载”语义；失败就是该语义失败 |
| `/api/v1/download/add` | 只提交 torrent，并让宿主按媒体参考自行识别媒体 | 只有 `torrent_in`，且仍具备可映射宿主媒体参考时 | `Response.success`、`data.download_id` | 成功表示宿主接受“torrent-only add”语义；失败不再自动切 `/download/` |
| 宿主 downloader runtime | 直接向宿主下载器模块提交 torrent/magnet | 音乐 torrent-only 候选，不具备可靠 `media_in` 或宿主影视媒体参考时 | `success`、`download_id`、`message` | 成功表示下载器已接受真实任务；失败表示真实下载器提交失败 |
| MusicPilot 本地 music preview | 对当前音乐 organize 上下文做目标路径预览 | 已有可用 metadata/context 与 organize 模板时 | `organize_status`、`target_library_path`、`target_relative_path` | 成功表示 MusicPilot 已完成本地音乐路径预览；失败表示 preview 输入不足 |
| 宿主底层 file/storage transfer | 对明确音乐源文件与目标路径执行 copy/move/link/softlink | 已有明确 organize input 与音乐目标路径 | `success`、`organize_status`、`target_path` | 成功表示宿主底层文件整理执行成功；失败就是 organize apply 失败 |
| `/api/v1/history/download` | 查询下载历史 | dispatch 成功后查询下载记录 | `path`、`download_hash`、`title`、`type` | 它只提供下载历史信息，不代表 organize 已可执行 |
| `/api/v1/history/transfer` | 查询整理历史 | 历史重放、补充查询 organize 输入时 | `src`、`dest`、`download_hash`、`src_fileitem`、`dest_fileitem` | 它只提供 transfer/history 语义，不代表新下载 handoff |

## 14.3 MusicPilot 场景调用规则

| 场景 | 主调用语义 | 说明 |
|---|---|---|
| `metadata -> search` | 默认 `/api/v1/search/title` | 只有拿到可靠宿主媒体 ID 时才改用 `/api/v1/search/media/{mediaid}`；二者是不同语义，不是 fallback |
| `candidate -> dispatch` | 有 `media_in` 走 `/api/v1/download/`；只有 torrent 且具备宿主媒体参考时走 `/api/v1/download/add`；音乐 torrent-only 候选走宿主 downloader runtime | 三条 dispatch 路径是三种确定语义，不再做推荐或自动换路 |
| `dispatch success -> path handoff` | 主来源 `/api/v1/history/download` | 只负责拿新派发后的下载记录 |
| `organize replay / supplemental lookup` | 补充来源 `/api/v1/history/transfer` | 只用于历史重放或补充查询，不再被包装成通用 fallback 引擎 |
| `organize preview` | MusicPilot 本地音乐路径预览 | 基于 metadata/context 与 organize 模板生成目标路径预览 |
| `organize apply` | 宿主底层 file/storage transfer runtime | 必须有明确 organize input；失败直接暴露 |
| `subscription run` | `metadata/detail -> search semantic -> candidate selection -> dispatch semantic` | 不再引入运行时策略决策层 |

## 14.4 关键字段的权威来源

| 字段 | 权威来源 | 补充来源 | 说明 |
|---|---|---|---|
| `download_id` | `/api/v1/download/`、`/api/v1/download/add` 或宿主 downloader runtime 的真实响应 | 无 | 以实际调用的下载接口或下载器提交响应为准 |
| `dispatch_result` | 真实调用的下载接口或下载器提交响应 | 无 | 不再由 recommendation 层重写 |
| `source_path` | `/api/v1/history/download.path` | `/api/v1/history/transfer.src` | 补充来源只用于历史重放/补充查询 |
| `source_filetype` | 基于权威 `source_path` 推导 | 无 | 没有 `source_path` 就直接失败 |
| `handoff_source` | 实际提供 `source_path` 的接口 | 无 | 如 `moviepilot.runtime.history.download` 或 `moviepilot.runtime.history.transfer` |
| `organize_input` | 传给宿主底层 file/storage transfer 的明确 fileitem/path 与目标文件路径 | 无 | 必须是显式整理输入 |
| `organize_status` | 宿主底层文件整理执行的成功/失败语义，或本地 preview/apply 记录状态 | 无 | 不再由策略解释层加工 |

## 14.5 插件机制与 HTTP API 的职责分工

MoviePilot 插件机制里：

- `get_api()`：插件暴露自己的 API
- `get_module()`：插件接管或重载宿主模块能力
- 链式事件：更适合承接 `TransferRename`、`TransferIntercept`、`ResourceDownload`、`WorkflowExecution` 等宿主内流程

当前 MusicPilot 仍以宿主 HTTP API 为主，是因为：

- 已经拿到了可联调、可验证的 search / download / transfer / history 语义
- 当前仓库目标是先保证外部插件侧接口语义稳定

但从宿主形态上看，以下能力后续更适合优先评估插件机制而不是继续扩 HTTP 抽象：

- organize 深度接入：`get_module()` / 链式事件
- storage / workflow：宿主模块直调或事件
- 宿主内工作流扩展：`get_actions()` / `WorkflowExecution`

## 14.6 当前不包含的设计

当前运行时不再包含：

- recommendation / preferred path 计算
- matrix 驱动的默认路径选择
- 隐式业务 fallback 决策层

`host_path_handoff` 的当前定义也已经收缩为：

- 新派发后的主来源：`history/download`
- 历史重放/补充来源：`history/transfer`

验证矩阵仍保留，但只作为验证产物，不参与运行时决策。

### 保留

- `mock / prefer_host / strict_host`
  - 仅用于环境与适配器选择
  - 不再作为运行时业务 fallback 引擎
- 已验证的真实宿主适配
- 明确的错误暴露

当前也不再鼓励以下组织方式继续扩散：

- 在 API 路由里直接串多个 `Service`
- 在单个 `Service` 中承担完整跨模块主流程
- 为每条新业务链继续发明一套脱离 `Chain` 的编排模式
- 为保留旧目录、旧命名、旧主流程入口而做兼容性双轨结构

## 14.7 当前推荐运行方式

1. 开发与测试环境：
   - 显式使用 `mock`
2. 真实宿主联调：
   - 使用 `prefer_host` 或 `strict_host`
   - 一旦进入 host 语义，失败直接暴露，不再偷偷切 mock
3. 验证矩阵：
   - 只用于回看真实样例，不驱动运行时选择

## 14.8 当前最小演示路径

1. `/health` 查看当前 active adapter 与 verification state
2. `/api/probe/health` 查看 capability summary
3. `history/transfer` 历史重放 organize 样例
4. 如需展示从搜索到下载，可优先演示 `search/title -> downloader runtime dispatch -> history/download -> organize apply`

不建议把以下路径当成“默认自动稳定路径”演示：

- `download_media + history/download -> organize apply`
- 任何仍然需要额外人工判断输入语义的组合

## 14.9 上层统一音乐媒体解析链基线

在当前固定宿主接口语义之上，MusicPilot 后续的上层统一语义确定为：

`MusicMediaInput -> MusicMetaBase -> MusicMediaInfo`

说明：

- 这是上层业务语义基线，不代表当前代码已经全部迁移完成
- `discovery -> detail` 只是这条统一音乐媒体解析链的一个消费场景，不再单独演化成新的特判体系
- 后续 metadata、search、subscription、acquisition、organize 上游识别，应优先向这条统一链路收敛

与当前阶段的关系：

- 当前固定的宿主接口语义、固定 handoff 来源和 organize 规则继续保持不变
- 需要重构的是上层“音乐实体如何被统一识别”的路径，而不是重新打开 recommendation / strategy / matrix 这类运行时决策层
