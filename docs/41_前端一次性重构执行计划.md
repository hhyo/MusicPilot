# MusicPilot 前端一次性重构执行计划

## 1. 目标

本轮前端工作不再做局部修补，而是围绕已经确定的后端统一音乐媒体解析链一次性重构前端主界面与前端数据层。

本轮重构的唯一后端主语义：

- `MusicMediaInput -> MusicMetaBase -> MusicMediaInfo`

本轮前端重构目标：

1. 前端完全切到统一音乐媒体解析链相关接口与类型。
2. discovery、metadata、subscription、search、settings 五个主模块一次性收口到新的页面结构。
3. 删除旧的 discovery target / resolution hints 思维模型，不再保留前端兼容层。
4. 视觉与交互直接切到 MoviePilot 风格的组件体系与页面结构，不再继续强化旧的 Element Plus 过渡页面。
5. 完成后直接以“新前端基线”作为后续继续开发的唯一前端主线。

## 2. 不做的事情

本轮不做：

- 继续兼容旧前端页面语义
- 保留旧的 `discovery-metadata.ts` 桥接层
- 局部修一个页面、保留其余旧状态
- 做数据库、调度、宿主后端的新能力扩展
- 做 frontend 和 backend 的双轨兼容

## 3. 当前现状判断

### 3.1 后端现状

后端已经完成主线切换：

- discovery 条目已产出 `media_input / meta_base / recognition_assessment`
- metadata detail 已通过统一链解析
- search job / subscription / organize 已围绕 `MusicMediaInfo` 收口
- `/metadata/lookup` 已废弃

### 3.2 前端现状

当前前端仍然处于“旧页面逐步补丁”的状态，主要问题：

1. 组件库和产品风格仍是过渡态，整体与 MoviePilot 风格不统一。
2. 页面结构是按阶段堆出来的，不是围绕统一链设计的。
3. discovery / metadata / search / subscription / settings 之间的流转不够统一。
4. 类型、服务与页面之间存在旧语义残留。
5. 旧页面有较多说明性文案和占位状态，不适合继续增量修补。

结论：

- 继续增量修补当前前端的收益已经很低。
- 最优路线是一次性重构主页面与前端数据流。

## 5. 目标前端架构

## 5.1 页面结构

前端主导航收成五个正式页面：

1. `Home`
   - 工作台总览
   - 当前 provider / discovery / subscription / acquisition / organize 状态概览
   - 统一入口导航

2. `Discovery`
   - 榜单列表
   - 榜单详情
   - 条目 recognition 状态
   - 从条目进入 metadata detail
   - 从条目创建订阅

3. `Library / Metadata`
   - Artist / Album / Track 搜索
   - metadata detail
   - 从 detail 创建 SearchJob / Subscription

4. `Subscriptions`
   - 订阅列表
   - 订阅详情
   - run 列表与 run 详情
   - 与 search / dispatch / organize 的链路结果查看

5. `Settings`
   - provider mode
   - RSS feed 配置
   - 当前 runtime 说明

### 5.2 数据层结构

服务层重构为：

- `services/music-media.ts`
  - 统一媒体解析接口
- `services/metadata.ts`
  - metadata search / detail
- `services/discovery.ts`
  - charts / chart detail / chart subscribe
- `services/subscriptions.ts`
  - subscriptions / runs
- `services/acquisition.ts`
  - search jobs / candidates / dispatch
- `services/settings.ts`
  - provider settings

不再保留额外桥接服务把旧 discovery 语义硬转成 metadata。

### 5.3 类型结构

类型分组：

- `types/music-media.ts`
- `types/metadata.ts`
- `types/orchestration.ts`
- `types/acquisition.ts`
- `types/settings.ts`

所有页面直接围绕后端正式 schema 定义，不保留旧前端自造过渡对象。

### 5.4 组件体系

本轮组件体系直接切到：

- `Vuetify`
- MoviePilot 风格的卡片式布局
- 与宿主一致的 `VCard / VBtn / VChip / VTextField / VNavigationDrawer / VTabs / VDialog` 主组件语义

不再继续围绕 `Element Plus` 组织页面。

## 6. 页面级重做计划

### 6.1 Home

目标：

- 从“说明页”升级成真正工作台
- 展示当前主链状态摘要
- 为 discovery / metadata / subscriptions / settings 提供清晰入口

执行要点：

- 保留轻量信息密度，不做大而空的英雄页
- 引入 4~6 个状态卡片
- 信息直接来自后端现有接口，不造假统计

### 6.2 Discovery

目标：

- 以“发现 -> 识别 -> 订阅”为主线重做
- 页面直接表达统一链状态：
  - `media_input`
  - `meta_base`
  - `recognition_assessment`

执行要点：

- 榜单卡片区 + 详情区
- hero entry + grouped entries
- 条目点击打开 metadata detail drawer
- 条目上直接显示识别状态，不再显示旧 conversion 话术

### 6.3 Search / Metadata

目标：

- 重做为“识别后的 metadata 工作页”
- 不再只是 seed 搜索演示页

执行要点：

- 搜索表单更轻
- 结果卡片直接表达 entity type、provider、detail 入口
- detail drawer 承接：
  - SearchJob 创建
  - Subscription 创建

### 6.4 Subscriptions

目标：

- 从 CRUD 列表升级成“主链执行台”

执行要点：

- 订阅列表
- 订阅详情
- 最近 runs
- run detail 中展示：
  - recognition 结果
  - search job
  - candidates
  - dispatch
  - organize

### 6.5 Settings

目标：

- 继续保持简洁
- 但视觉与结构贴近新前端整体

执行要点：

- provider mode
- RSS feeds JSON
- 运行时说明卡片
- 不做复杂 feed CRUD

## 7. 视觉与交互原则

本轮按 MoviePilot 风格靠拢，但不做盲目照搬。

原则：

1. 卡片化布局
2. 较强的信息层级
3. 减少长段说明文案
4. 一个页面只围绕一个主任务
5. 不再继续扩 Element Plus 过渡风格的“后台管理表单感”
6. 组件选择与页面骨架优先贴近宿主实际使用的 Vuetify 语义

技术方向：

- 保持 `Vue 3 + TypeScript + Vite`
- 新增并切换到 `Vuetify`
- 保留当前 remote component 入口
- 页面样式层抽为统一的 MoviePilot 风格卡片/栅格/工具栏体系

## 8. 执行顺序

一次性执行顺序固定为：

1. 切换组件体系与基础设施（Vuetify、应用创建、主题、布局）
2. 重建前端类型与服务层
3. 重做 metadata detail drawer
4. 重做 Discovery 页面
5. 重做 Search / Metadata 页面
6. 重做 Subscriptions 页面
7. 重做 Settings 页面
8. 重做 Home 页面
9. 跑前端单测与 build
10. 打包 plugin runtime
11. 做真实页面截图与本地运行验证

## 9. 完成定义

本轮前端重构完成时，应满足：

1. 前端不再依赖旧 discovery target 思路。
2. 所有主页面都能消费统一链后的后端数据。
3. 关键交互都能真实跑通：
   - discovery 条目打开 detail
   - metadata detail 创建 search job
   - metadata detail 创建 subscription
   - subscription 查看 run 详情
   - settings 读写 provider settings
4. `pnpm test -- --run` 通过。
5. `pnpm build` 通过。
6. `python3 scripts/package_plugin.py` 通过。
7. 提供关键页面真实截图。

## 10. 风险与处理策略

### 风险 1：前后端字段已变化，旧组件大面积失配

处理：

- 不修补旧组件，直接按新 schema 重写组件输入

### 风险 2：页面改动面大

处理：

- 严格按固定顺序一页页完成
- 每完成一个页面就回跑局部测试和 build

### 风险 3：打包脚本污染 runtime 静态产物

处理：

- 仅在最终验证阶段打包
- 若打包带来与本轮无关静态差异，按当前前端重做结果统一收口，不夹带无关历史残留
